## 3. Slack adapter and authority model

Sound: event acceptance is fail-closed (team, app, channel, owner, no bot/subtype, ts format, length); durable SQLite inbox before ack; UNIQUE(team,channel,ts) dedupe; restart recovery never re-sends an in-flight post; channel privacy rechecked before generation and before send; replies are `plain_text` blocks with `parse:'none'` and no unfurls; systemd unit is properly hardened (DynamicUser, ProtectSystem=strict, ProtectHome, MemoryMax); credential bridge and installer never log or argv-pass tokens; no token strings anywhere on disk.

Findings, ranked:

- **S1 Owner messages are silently and permanently dropped after ~30 s of model unavailability. CONFIRMED.** `src/slack/worker.js:30-39` marks `failed` on the third generation failure; drains retry every 15 s (`main.js:49`); the Qwen circuit breaker opens for 30 s after 3 failures (`src/claude.js:108`, `circuit-breaker.js:19-27`) so attempts 2–3 fail instantly. Same terminal path for reply >10,000 chars, `max_tokens` stop, and the 100/day call cap. Nothing is posted to Slack and `failed` rows are never revisited.
- **S2 Definitive Slack API rejections (429, `invalid_blocks`, `msg_too_long`) are classified `uncertain` and never retried. CONFIRMED.** `worker.js:48-59` treats every `postMessage` exception uniformly; the SDK error's `.data.error` is never inspected. `uncertain`, `failed` and `blocked` are all dead-end states with no reconciliation or operator surfacing (`store.js:19-23`; `counts()` is test-only).
- **S3 Error codes are discarded before logging. CONFIRMED.** `main.js:66` reduces `slack_invalid_configuration:<field>`, `slack_wrong_installation`, `slack_core_model_mismatch` etc. to the bare word `startup_failed`; `worker.js:26/36/46/55` likewise. With `StartLimitBurst=5` the unit ends up stopped with five identical lines. Redacting source text is right; redacting the error class is not.
- **S4 Recall exists only inside a Slack thread. CONFIRMED.** `policy.js:17` sets `thread = thread_ts || ts`, so every top-level channel message is a new root with empty history (`store.js:37-41`). A follow-up typed as a new channel message has zero context. History also requires `state='sent'`, so a delivered-but-`uncertain` reply is invisible to later turns.
- **S5 Docs, manifest and policy disagree. CONFIRMED.** The deployed `docs/clint-slack-release.md:72-73` lists scopes `app_mentions:read, chat:write, groups:read` and says "Mention @Clint"; the manifest adds `groups:history` + `message.groups`; `policy.js:7` accepts any un-mentioned owner message. The worktree copy of the doc was updated after staging; the deployed copy is stale. `SLACK_MODEL_ID` is a zod literal (`config.js:26`), not configurable as the doc presents it.
- **S6 Planner injects owner-private facts regardless of scope. CONFIRMED mechanism.** `src/task-planner.js:92-97` (family names, London–York travel) is sent on any `needsPlan` route with no `permitsPrivateContext()` gate. Harmless while James is the only member; a scope violation the moment the channel gains a second member (the stated LQ target).
- **S7 Colleague-mode prompt names the projects it is meant to hide. CONFIRMED.** `prompt.js:160` SELF_AWARENESS lists ATLAS, SOVREN, Clint AGI unconditionally; `tools/definitions.js:658` lists atlas/clint-agi/sovren/spire in `project_read`. The colleague output filter (`output-filter.js:26-35`) blocks `atlas` but not `sovren`, `spire`, `clint-agi`.
- **S8 `EVO_MEMORY_ENABLED=false` is not honoured by the memory client. CONFIRMED.** `src/memory.js` never reads it; `memory_search` is offered for recall/system and POSTs the query to :5100. `filterScopedMemories` then drops every row (none carry a `slack:` chatJid), so nothing leaks, but the query text leaves the process and the doc's "archive memory disabled" is only true for cortex streams. In `open` mode the filter is bypassed by design and Slack would see the whole WhatsApp archive.
- **S9 Core writes outside `data/` under the read-only sandbox. CONFIRMED path.** `usage-tracker.js:27` writes `auth_state/usage.json` under `/opt/clint-slack/current` every 10 s and swallows the EROFS (`:60,70`). Harmless today; a template for future opaque failures.
- **S10 Live probe does not exercise the deployed policy. CONFIRMED.** `scripts/slack-live-probe.mjs:7` runs `mode:'project'` with a synthetic blocked topic; deployment is `colleague` with none.
- **S11 Cloud-credential guard is incomplete. CONFIRMED, latent.** `slack/core-config.js:11` rejects only Anthropic/MiniMax/Google keys; Tavily/Brave/Perplexity/SearXNG pass. The current `runtime.env` has none of them, so external search is unreachable today (SearXNG default is loopback :8888).
- **S12 Owner messages carrying a `subtype` (`file_share`, `thread_broadcast`) are ignored with no notice. CONFIRMED.** `policy.js:11`.
- **S13 Chunking at fixed 2,500 UTF-16 units can split a surrogate pair. PLAUSIBLE.** `policy.js:34`; Slack would reject the payload → S2.
- **S14 Head-of-line blocking with no adapter-level generation timeout. PLAUSIBLE.** `worker.js:15` retries the failing message first every drain; worst case ≈10 min per message; `TimeoutStopSec=110` then SIGKILL.
- Minor: no `unhandledRejection` handler in the Slack process (Sentry init is WhatsApp-only); classifier and intent detection run over the untrusted history blob (`router.js:192`); "WhatsApp style" survives in `DIRECT_TRIGGER_PROMPT:232` and `TODO_RULES:111`; `[Delivery correction…]` is appended inside `[Current message]` so the retry is re-classified on the correction text.
